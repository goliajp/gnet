# gnet v1.2 — detailed plan

> **Scope contract.** v1.2 closes three loops that v1.1 deliberately
> left open: (1) the dispatcher → daemon control channel that makes
> the v1.1 `501 Not Implemented` wire-contracts real, plus the macOS
> native app that consumes the daemon's `/local/*` admin surface;
> (2) multi-user collaboration (`Member` role hierarchy) on networks;
> (3) the SaaS-side ASVS L1 follow-ups that the v1.1 hardening sweep
> deliberately deferred. As with v1.1 this is one release, not a
> sequence of interim ships; the internal fleet dogfoods until the
> whole thing is industrial-grade before cut-over.
>
> This document is the **engineering plan**, not the release
> roadmap. It covers what gets built, by what boundaries, in roughly
> what order; it does not promise dated milestones.

---

## 1. Product shape

Three feature axes; each is independent enough to ship-test on the
internal fleet on its own, but all three land in the same release so
the v1.1 → v1.2 cut-over is one operator action per host.

**A. Control channel + native app.** v1.1 shipped the
URL surface; v1.2 fills in the implementation.

- Daemon's `/local/{alias,join,quit,restart,upgrade}` go from `501`
  to fully implemented operations against the running node.
- A new **dispatcher → daemon push channel** lets the dispatcher
  initiate operations (kick, rotate-key, restart) at the daemon
  instead of waiting for the daemon to poll.
- The dispatcher's existing `POST /api/devices/{id}/{rotate-key,
  restart}` endpoints go from `501` to real, riding on that channel.
- A **macOS menubar app** (SwiftUI, `mac/` in this repo) consumes
  the daemon's local admin surface; install-time provisions the
  one-shot token to the OS keychain (the daemon admin token file
  already enforces mode `0o400`).

**B. Multi-user collaboration (`Member` role hierarchy).** v1.1
ships single-owner networks; v1.2 lets a network owner invite
other users and grant `admin` / `member` / `viewer` roles on the
network. Audit log captures the actor identity per role, so a
shared network has provable accountability.

**C. SaaS hardening — ASVS L1 follow-ups.** The defensive controls
v1.1 explicitly deferred (`SECURITY.md` walkthrough):
Content-Security-Policy + Permissions-Policy headers, per-route
body limits, per-IP login throttle (the v1.1 per-account throttle
stays), CAPTCHA on signup, and `audit_log` tamper-evidence (hash
chain). Each is small on its own, but the bundle closes the v1.1
"L1 with deferrals" status to "L1 with no deferrals".

**Hard rules** (unchanged from v1.1):

1. The daemon (`gnet`) stays zero-deps. The control channel adds
   zero crates.io deps; daemon-side it's still hand-rolled HTTP/1.1
   parsing (the §17.9 pattern) talking to dispatcher over the same
   `curl` shell-out the daemon already uses.
2. v1.0 wire untouched. `/peers`, `/join`, `/endpoint-report`,
   daemon UDP wire — bit-identical. A v1.0 daemon on a v1.2 fleet
   keeps running unaware.
3. **All v1.2 features still opt-in via env** where they touch the
   daemon. A v1.1 daemon with `GNET_LOCAL_ADMIN_ENABLE=0` (default)
   exposes no local-admin surface; the native app is the only
   consumer and turns it on explicitly during install.

## 2. Architectural inversion (vs. v1.1)

v1.1's wire surface was strictly **pull**: daemons polled
`/peers`, dispatcher waited for `/api/internal/snapshot` pushes,
the SPA polled the admin API. There was no path from
"administrator clicks a button" to "running daemon changes
behaviour" inside one second.

v1.2 adds a single inversion: a long-poll-ish channel from each
daemon back to its dispatcher, structured as the daemon
**asking** the dispatcher "any pending operations for me?". The
direction stays daemon-initiated (so NAT / firewall traversal
stays trivial — the daemon already initiates `/endpoint-report`
calls), but the dispatcher gets to *answer* with a queued
operation instead of `200 OK / no-op`.

This is the minimum mechanism that lets kick / rotate-key / restart
land at the daemon within seconds without:

- exposing a new inbound port on the daemon side,
- introducing a new persistent-connection protocol (no WebSocket,
  no gRPC, no SSE),
- breaking the v1.0 wire (the v1.0 daemon never asks for
  operations, so v1.2 dispatcher always answers "nothing" to it).

The control channel rides on top of `/api/internal/snapshot`
(the daemon's existing push endpoint): the dispatcher's response,
currently `204 No Content`, gains an optional JSON body listing
queued operations. v1.0 daemons ignore the body; v1.2 daemons act
on it.

## 3. Components

### 3.1 Existing (untouched in v1.2 unless noted)

- `crates/gnet` — daemon. New code inside `local_admin.rs` to
  implement the five `501` stubs; new code inside `node/control.rs`
  (TBD module) to act on operations returned by the dispatcher
  snapshot reply. No new deps.
- `crates/gnet-relay-server` — relay. Unchanged unless ASVS L1
  audit_log tamper-evidence (Phase C) wants the relay's lite admin
  surface joined to the chain (optional).

### 3.2 Reshaped

- `crates/gnet-discover` — dispatcher. Snapshot reply gains an
  `ops` field; new internal table `device_pending_ops` queues the
  ops; `rotate_key` / `restart` 501 stubs become real handlers
  that enqueue.
- `crates/gnet-console` — console. Member invite + accept flow;
  role-aware UI gates write affordances; new schema (`network_members`,
  `network_invitations`) plus migrations.

### 3.3 New

- `mac/` — macOS SwiftUI menubar app. Reads the daemon's
  `/local/status` for the menu state, fires `/local/{alias, restart,
  join, quit, upgrade}` from menu actions, surfaces install via a
  signed `.dmg` (notarised; signing identity TBD).
- `crates/gnet-discover-schema/migrations/000X_*` —
  `device_pending_ops` table, `audit_log` hash-chain column,
  `network_members` table, `network_invitations` table.
- `console/src/routes/console/Members.tsx` etc. — member
  management UI.

### 3.4 Frontend

The SPA gains member views (invite / role change / removal) and
loses no functionality. Headers middleware grows CSP +
Permissions-Policy emission. The dispatcher's standalone SPA
inherits the same headers automatically.

### 3.5 Native node app — **shipped in v1.2**, lives at `mac/`

The directory was a placeholder in v1.1 (README only). v1.2 fills
it with the SwiftUI Xcode project.

**Talks to:** the daemon's localhost admin (`http://127.0.0.1:6019`
by default, configurable per env), authenticated by the file-mode-
`0o400` token at `/Library/Application Support/gnet/admin_token`
(per the v1.1 §17.9 contract).

**Bundle install** (one-time, by `make install` shipped with the
.dmg):

- writes the daemon admin token file under `Library/Application
  Support/gnet/` with `chmod 400`,
- copies the token into the user keychain,
- writes a launchd plist that boots the daemon with
  `GNET_LOCAL_ADMIN_ENABLE=1`,
- triggers a `launchctl bootstrap` so the menubar app finds a
  daemon already running.

**Signing identity:** GOLIA K.K. Apple Developer account
(`lihao@golia.jp`). The Developer ID + notarisation profile lives
in the operator's keychain; the release pipeline references it by
name (`DEVELOPER_ID_APPLICATION` / `APPLE_NOTARIZE_PROFILE` env)
so the secret never enters the repo.

**Distribution:** signed + notarised `.dmg` attached to the GH
Release; no Mac App Store distribution in v1.2.

**Out of scope for v1.2:** Linux GUI / Windows app / cross-platform
TUN. The daemon's `/local/*` surface is portable, so a third-party
GUI on any OS is unblocked once they implement against it.

## 4. Data ownership boundary (delta vs. v1.1)

| Concept | Owner | Change |
|---|---|---|
| Network members | **console** PG | new table `network_members` |
| Pending invitations | **console** PG | new table `network_invitations` |
| Per-device pending operations | **dispatcher** PG | new table `device_pending_ops` |
| Local admin token (daemon side) | **filesystem** + **keychain** (macOS) | already in v1.1; native app populates |
| Audit log hash chain anchor | **dispatcher** PG | new column on `audit_log` |

The console-side member model lives on the SaaS side because Mode
A users invite each other through `gnet.golia.jp`. A self-host
dispatcher in Mode B has its own multi-user surface via its existing
`admin_users` table (which already supports >1 row); v1.2 adds the
same `role` column there for symmetry but Mode B doesn't get the
invite-by-email UX (no mailrs binding in Mode B by default).

## 5. API surface

### 5.1 Daemon localhost admin — v1.1 stubs become real

| Method | Path | v1.1 | v1.2 |
|---|---|---|---|
| GET | `/local/status` | implemented | unchanged |
| PUT | `/local/alias` | 501 | implemented — renames self, persists to config, broadcasts via next snapshot |
| POST | `/local/join` | 501 | implemented — calls dispatcher `/join`, persists token + endpoint to config |
| POST | `/local/quit` | 501 | implemented — drops session, removes config, daemon enters idle state |
| POST | `/local/restart` | 501 | implemented — graceful `re-exec`; the supervising launchd/systemd brings the process back up; the menubar app reconnects on retry |
| POST | `/local/upgrade` | 501 | implemented — downloads + verifies signature on the targeted binary, swaps it, triggers `/local/restart` |

All five are atomic at the daemon side (no half-state on
failure). The response body is the same JSON shape as the
existing `/local/status`, reflecting the new state.

### 5.2 Dispatcher → daemon control channel (new)

The dispatcher's existing `POST /api/internal/snapshot` reply
shape changes from `204 No Content` to either `204` (when no
pending ops) or `200 OK` with a JSON body:

```json
{
  "ops": [
    {"op_id": "uuid", "op": "kick", "args": {}},
    {"op_id": "uuid", "op": "rotate_key", "args": {"new_pubkey_hex": "..."}},
    {"op_id": "uuid", "op": "restart", "args": {}}
  ]
}
```

The daemon executes them in order; for each one it sends a
follow-up `POST /api/internal/snapshot/ack` with `{op_id, status:
"ok|error", detail: "..."}`. The dispatcher marks the row
`completed_at` (success) or `failed_at` + `last_error` (error,
auto-retried up to N times with backoff, then dropped).

`device_pending_ops` table holds the queue. Operator-side endpoints
(`POST /api/devices/{id}/kick` / `rotate-key` / `restart`) enqueue
a row; the existing kick (`removed_at` soft-delete in §17.7) stays
as the canonical "daemon should stop existing" mechanism, but
rotate-key + restart leave the row alive and queue the op.

### 5.3 Console — Member API (new)

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/networks/{id}/members` | session | list members (incl. roles) |
| POST | `/api/networks/{id}/invitations` | session, owner/admin | invite by email |
| GET | `/api/networks/{id}/invitations` | session, owner/admin | list pending |
| DELETE | `/api/networks/{id}/invitations/{inv_id}` | session, owner/admin | revoke pending |
| POST | `/api/invitations/{token}/accept` | session (any) | accept (joins the network with the invited role) |
| PATCH | `/api/networks/{id}/members/{user_id}` | session, owner | change role |
| DELETE | `/api/networks/{id}/members/{user_id}` | session, owner | revoke |

Invitations are deterministic-token (same derivation pattern as
the v1.1 federation tokens — 32 random bytes hex, SHA-256 stored,
TTL one week, single-use). Email goes through mailrs (the same
transport v1.1 added), using the v1.1 `MAILRS_*` env binding —
the superadmin (`lihao@golia.jp`) login that v1.1 ships with is
fine for v1.2; the dedicated mailrs service account is tracked on
the 1.1.x patch lane and does not block v1.2.

### 5.4 SaaS hardening additions (no new endpoint shape)

- Headers middleware emits CSP + Permissions-Policy in addition to
  the v1.1 set; CSP is `default-src 'self'; img-src 'self' data:;
  script-src 'self'; style-src 'self' 'unsafe-inline';
  connect-src 'self'`; the SPA is built to match.
- Per-route body limits via axum's `DefaultBodyLimit` layer; the
  one or two endpoints that legitimately accept larger bodies
  (audit-log search export?) declare their own larger limit.
- **Per-IP login throttle — proxy-header trust model.** SaaS Mode A
  runs behind Caddy on t01; v1.2 reads the client IP from
  `X-Real-IP` (set by Caddy `reverse_proxy`) when the peer's socket
  address belongs to the loopback the Caddy reverse-proxy reaches us
  on. Gated by `GNET_CONSOLE_TRUST_PROXY=caddy` (default in the
  SaaS compose; **off** by default — self-host Mode B does not
  publish behind a known reverse-proxy by default and the socket
  peer is the right source). When the gate is off the throttle key
  is the socket peer; spoofing requires owning the underlay path
  to the host. Throttle key is the same per-account counter pair
  from v1.1 plus a new per-IP counter; the looser of the two trips
  the 429.
- `audit_log.prev_hash` column: each row's `hash = SHA3-256(prev_hash
  || row_canonical_form)`; an operator-facing `GET /api/audit/verify`
  walks the chain and reports the first break.

## 6. Auth + federation — Member-aware

### 6.1 Role hierarchy

- **owner** — only one per network; can grant/revoke any role
  including transferring ownership.
- **admin** — can invite/revoke members up to `admin`; cannot
  transfer ownership; can write device + relay state.
- **member** — can read all network state; can rename their own
  device (the one whose `device_token` they hold); cannot kick or
  rotate-key other devices.
- **viewer** — read-only on all network state.

`session.role` carries the role; every write handler checks
`role >= required_role` at entry. The existing `audit_log.actor_id`
already records the user_id; v1.2 adds `audit_log.actor_role` so a
later audit reader sees "this kick was an `admin` action" without
needing to look up the user's role at audit time.

### 6.2 Federation + members

A federated dispatcher (Mode C) trusts whoever the console says.
The federation token derivation (v1.1 §6.3) already keys on user_id
+ label + endpoint; v1.2 doesn't change that, but the console's
proxy forwarder learns to attach `X-Gnet-Actor-Role` so the
dispatcher can store the role in its audit row. The dispatcher
checks the role; the trust boundary stays at "any bearer of this
federation token is allowed to act on this network as whatever
role the console says" — the console is the only thing that mints
those, and the console enforces the role check before forwarding.

## 7. Multi-tenancy (delta vs. v1.1)

v1.1 multi-tenancy assumed single-owner networks; v1.2 multi-user
networks fit on top of the same per-network row layout — a `Network`
still has exactly one owner, plus zero-or-more `Member` rows.

The `gnet.golia.jp/` landing copy gains a small mention of "invite
your team" but stays focused on the same audience (one user
managing zero-or-more networks). The marketing site is not the
plan's load-bearing piece.

## 8. Schema sketches

### 8.1 Dispatcher schema additions

```sql
-- device_pending_ops: queue of operations the dispatcher wants the
-- daemon to execute next time it pushes a snapshot.
CREATE TABLE device_pending_ops (
    id            UUID PRIMARY KEY,
    network_id    UUID NOT NULL REFERENCES networks(id) ON DELETE CASCADE,
    device_id     UUID NOT NULL REFERENCES devices(id)  ON DELETE CASCADE,
    op            TEXT NOT NULL CHECK (op IN ('kick','rotate_key','restart','upgrade')),
    args          JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    delivered_at  TIMESTAMPTZ,
    completed_at  TIMESTAMPTZ,
    failed_at     TIMESTAMPTZ,
    attempts      INT NOT NULL DEFAULT 0,
    last_error    TEXT
);

CREATE INDEX device_pending_ops_device_pending_idx
    ON device_pending_ops (device_id) WHERE completed_at IS NULL AND failed_at IS NULL;

-- audit_log hash chain. Each new row's hash folds in the previous
-- row's hash so any in-place edit / deletion breaks the chain
-- from that point forward.
ALTER TABLE audit_log ADD COLUMN actor_role TEXT;
ALTER TABLE audit_log ADD COLUMN row_hash   BYTEA;  -- SHA3-256(prev_hash || canonical_form)
ALTER TABLE audit_log ADD COLUMN prev_hash  BYTEA;  -- NULL for the first row per network
```

### 8.2 Console schema additions

```sql
CREATE TABLE network_members (
    network_id   UUID NOT NULL REFERENCES user_networks(id) ON DELETE CASCADE,
    user_id      UUID NOT NULL REFERENCES users(id)         ON DELETE CASCADE,
    role         TEXT NOT NULL CHECK (role IN ('owner','admin','member','viewer')),
    granted_by   UUID REFERENCES users(id),
    granted_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (network_id, user_id)
);

CREATE TABLE network_invitations (
    id           UUID PRIMARY KEY,
    network_id   UUID NOT NULL REFERENCES user_networks(id) ON DELETE CASCADE,
    invited_by   UUID NOT NULL REFERENCES users(id),
    invited_email TEXT NOT NULL,
    role         TEXT NOT NULL CHECK (role IN ('admin','member','viewer')),
    token_hash   BYTEA NOT NULL,
    expires_at   TIMESTAMPTZ NOT NULL,
    accepted_at  TIMESTAMPTZ,
    revoked_at   TIMESTAMPTZ
);
CREATE UNIQUE INDEX network_invitations_token_uniq ON network_invitations (token_hash);
```

`user_networks` (today: one row per user-owned network) gets
re-interpreted: the row still represents "this user's view of this
network", but **the row's existence is now implied by `network_members`**.
The existing federation token derivation keys on (user_id, label,
endpoint), so each member of a shared network gets their own
deterministic bearer.

## 9. Plan execution — §18 phase breakdown

Phases are roughly dependency-ordered; ones in the same column can
run in parallel inside one engineering session.

| Phase | Content | Trigger |
|---|---|---|
| §18.1 | `device_pending_ops` schema + dispatcher enqueue path; snapshot reply body extension; daemon JSON parse (still hand-rolled) + ack endpoint | v1.1 ship + dogfood pass |
| §18.2 | Dispatcher write paths (`rotate-key`, `restart`) flip from 501 to real, enqueuing into §18.1 | §18.1 wire stable |
| §18.3 | Daemon `/local/{alias,join,quit,restart,upgrade}` implementations; supervisor (launchd / systemd) integration for `restart` + `upgrade` | §18.1 done (status already real in v1.1) |
| §18.4 | `mac/` SwiftUI menubar app — first version reads `/local/status` only | §18.3 GET surface stable |
| §18.5 | `mac/` writes (alias / restart / join / quit / upgrade) + signed `.dmg` + notarisation + install script | §18.3 write surface stable |
| §18.6 | `network_members` + `network_invitations` schema; basic GET endpoints + member-aware require_login | independent of §18.1–5 |
| §18.7 | Member invite + accept flow + email send via mailrs + SPA invite UI | §18.6 schema + mailrs (v1.1) |
| §18.8 | Role enforcement on every write handler; `audit_log.actor_role` recorded | §18.6 schema |
| §18.9 | SaaS hardening — CSP + Permissions-Policy + per-route body limits | independent |
| §18.10 | SaaS hardening — per-IP login throttle + signup CAPTCHA | independent (per-IP needs proxy-header trust decision) |
| §18.11 | SaaS hardening — `audit_log` hash chain + `GET /api/audit/verify` | independent |
| §18.12 | macOS native app polish + release pipeline (`.dmg` build automated in `release.yml` matrix) | §18.4–5 done |

Phases §18.6–8 form the **Member track**; §18.1–5 form the
**control + native app track**; §18.9–11 form the **hardening
track**. The three tracks are loosely coupled; cut-over to v1.2
needs all three to be green on the internal fleet.

## 10. Out of scope for v1.2 (explicit)

- **Linux / Windows native apps.** The daemon's `/local/*` surface
  is portable, but v1.2 only ships the macOS consumer. Third-party
  ports against the same wire are welcome.
- **Mobile clients.** Cross-platform TUN remains off the gnet
  path; ROADMAP 2.x discusses if-and-when.
- **ACL / policy rules / subnet routes / exit nodes.** Wire-break
  changes; tracked under ROADMAP 2.x.
- **Publishing the leaf stones to crates.io.** Independent track;
  the dry-run gate is already green.
- **Mode B SaaS-equivalent email invitation.** Mode B's dispatcher
  doesn't bind mailrs by default; invitations in Mode B happen by
  copy-pasting the invitation link, no email send.
- **Cross-network member transfer.** A user invited to network A
  is not invited to network B; the model stays per-network.
- **Dedicated mailrs service account.** Stays on the 1.1.x patch
  lane — Member invitations in v1.2 go out via the v1.1 superadmin
  login binding (`lihao@golia.jp`). Splitting to a service account
  is independent and can land in any 1.1.x patch.

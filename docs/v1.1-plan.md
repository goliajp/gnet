# gnet v1.1 — detailed plan

> **Scope contract.** v1.1 ships the full self-host + SaaS surface in one
> release. No interim ship; we keep dogfooding internally until the whole
> thing is industrial-grade. The fleet (t01/t02/lx64/mini) is the first user,
> and we don't cut over from v1.0 → v1.1 in production until v1.1 has run
> the internal fleet cleanly for an extended observation window.
>
> This document is the **engineering plan**, not the release roadmap. It
> covers what gets built, by what boundaries, in roughly what order; it does
> not promise dated milestones.

---

## 1. Product shape

Three deployment modes, all first-class:

- **A. SaaS hosted** (`gnet.golia.jp`). User signs in via OAuth, gets a
  network managed entirely on our infrastructure (hosted dispatcher + relay
  + PG). User installs only the node client.
- **B. Self-host** (open-source). User runs the whole stack themselves via
  `docker-compose up` (dispatcher + relay + PG + Valkey). Never talks to
  `gnet.golia.jp`. This is the open-source basis — it must be fully usable
  with no SaaS dependency.
- **C. Hybrid / federated.** User self-hosts dispatcher + relay but signs
  in via `gnet.golia.jp` to manage them through the SaaS console
  (federation handshake). For users who want SaaS UX over their own
  infrastructure.

**Hard rules.**

1. The daemon (`gnet`) stays zero-deps. Nothing in v1.1 touches its
   dependency tree.
2. Self-host mode must work with **zero outbound calls** to anything we
   host. No telemetry beacon, no license check, no update ping.
3. Mode A and Mode B share **the same dispatcher binary**, the same admin
   API, the same SPA. The SaaS deploy is just one tenant of the same
   software running on our hardware.

## 2. Architectural inversion (vs. ROADMAP rev1)

The original v1.1 plan put the SaaS console at the center: console owns PG,
dispatcher pushes state into console. Self-host requirement (Mode B) makes
that impossible — a self-hosted user can't depend on a SaaS-only PG schema
to run their network. So the architecture is inverted:

**Dispatcher is the admin source-of-truth.** It owns its network's PG,
its admin API, its admin SPA, its local accounts. It's a complete product
on its own. SaaS console is a thin federation layer on top.

```
+-----------------------------+        +-----------------------------+
|      gnet.golia.jp          |        |   self-host docker-compose  |
|   (Mode A & C: SaaS)        |        |          (Mode B)           |
|                             |        |                             |
|  +-----------------------+  |        |  +-----------------------+  |
|  | console binary        |  |        |  | dispatcher binary     |  |
|  |   - OAuth / accounts  |  |        |  |   - admin API         |  |
|  |   - user↔network map  |  |        |  |   - admin SPA         |  |
|  |   - federation router |  |        |  |   - local accounts    |  |
|  |   - PG (console)      |  |        |  |   - PG (dispatcher)   |  |
|  +-----------+-----------+  |        |  +-----------+-----------+  |
|              |              |        |              |              |
|              | federation   |        |              | overlay      |
|              v              |        |              v              |
|  +-----------------------+  |        |  +-----------------------+  |
|  | dispatcher(s)         |  |        |  | relay binary          |  |
|  |   - same binary as B  |  |        |  | + nodes (gnet daemons)|  |
|  | relay(s)              |  |        |  +-----------------------+  |
|  +-----------------------+  |        +-----------------------------+
+-----------------------------+
```

In Mode A, gnet.golia.jp runs **both** the console (federation) and the
backing dispatcher(s); the console proxies the user's operations into a
dispatcher we host on their behalf. In Mode B, no console — the user goes
straight to `https://dispatcher.local/`. In Mode C, the user's
self-hosted dispatcher registers itself with `gnet.golia.jp` via a
federation handshake (paste a token); thereafter the SaaS console can
proxy operations to it.

## 3. Components

### 3.1 Existing (untouched in v1.1 unless noted)

- **`crates/gnet`** — overlay daemon. Zero-deps. v1.1 adds **one
  localhost admin endpoint** (for the future native node app, §3.5);
  otherwise untouched.
- **`crates/gnet-crypto`, `gnet-wire`, `gnet-noise`, `gnet-tun`,
  `gnet-punch`, `gnet-relay`, `gnet-rand`, `gnet-hex`, `gnet-config`**
  — pure data-plane stones. Not touched.
- **`crates/gnet-bench-compare`** — bench harness. Not touched.

### 3.2 Reshaped

- **`crates/gnet-discover`** — the coord becomes the **dispatcher**. Gains:
  admin HTTP API (port distinct from the current `:65432` coord port),
  PG-backed state replacing `state.json`, local account / session
  handling, embedded admin SPA via `include_dir!`, federation
  trust-store, audit log. State migration from `state.json` → PG is a
  one-shot importer the dispatcher runs on first start.
- **`crates/gnet-relay-server`** — the relay gains a lite admin: admin
  HTTP API, local account, embedded SPA (lighter — peer table, traffic
  counters, stale entries). Forwarding hot path untouched.

### 3.3 New

- **`crates/gnet-console`** *(skeleton already exists, phase B baseline)*
  — SaaS-only federation binary. Owns: accounts, OAuth, email/password,
  `user → network → dispatcher_endpoint` mapping, federation token
  vending, audit aggregation. **Does not** own device/network state —
  proxies operations to the responsible dispatcher.
- **`crates/gnet-console-schema`** *(skeleton already exists)* — PG
  schema for the console (SaaS) side.
- **`crates/gnet-discover-schema`** — PG schema for the dispatcher side.
  Sibling of `gnet-console-schema` to keep migration ownership clean.
- **`crates/gnet-adminapi`** — shared types + (small) trait definitions
  for the admin API contract. Both dispatcher and console depend on it;
  dispatcher implements the server, console implements the federation
  proxy. Optional: if the types fit naturally in `gnet-console-schema`
  and `gnet-discover-schema`, fold there and skip this crate.

### 3.4 Frontend

- **`console/`** at the repo root — single React 19 + Vite 7 +
  TailwindCSS 4 + react-router + @tanstack/react-query + Jotai SPA.
- Build output `console/dist/` is embedded into **three** binaries via
  `include_dir!`:
  - dispatcher (`gnet-discover`)
  - relay (`gnet-relay-server`)
  - console (`gnet-console`)
- The SPA detects the host's role at boot (`GET /api/host-role`) and
  swaps the visible tabs accordingly:
  - **dispatcher** → Devices, Network, Relays, Audit, Settings
  - **relay** → Peers, Traffic, Audit (lite), Settings
  - **console** → Networks (list), per-network proxy view, Account, Audit
- Auth path is per-role too: dispatcher/relay show local
  username/password; console shows OAuth + email.

### 3.5 Native node app — **deferred to v1.2**, but lives in this repo

macOS menubar app (SwiftUI), talks to the local `gnet` daemon over a
**localhost-only HTTP admin endpoint with a one-shot install-time
token** stored in the OS keychain.

Per §16.7 the app lives at `mac/` in this repo (not a sibling repo), so
the daemon's localhost admin contract and its only consumer stay in
lockstep with a single workspace version. v1.1 ships *only* the daemon
admin endpoint, gated by env (off by default unless
`GNET_LOCAL_ADMIN_ENABLE=1` until the v1.2 app ships), so v1.2 can land
the app without re-touching the daemon. The `mac/` directory may be
empty in v1.1 except for a README pointing at v1.2.

## 4. Data ownership boundary

| Concept | Owner |
|---|---|
| User account, OAuth identity, email/password | **console** PG |
| User ↔ network ↔ dispatcher endpoint mapping | **console** PG |
| Federation tokens (SaaS → self-host dispatcher trust) | **console** issues, **dispatcher** stores |
| Local admin account (Mode B self-host login) | **dispatcher** PG |
| Network meta (name, overlay CIDR, settings) | **dispatcher** PG |
| Devices (current state.json content) | **dispatcher** PG |
| Per-device admin snapshot (ring buffer) | **dispatcher** PG |
| Audit log (local) | **dispatcher** PG |
| Audit aggregate (cross-network) | **console** PG (read-replica of dispatcher audit + console's own events) |
| Active sessions | **Valkey** (per binary — dispatcher has its own, console has its own) |
| Relay forwarding table (in-memory, hot) | relay process memory (not PG) |
| Relay metrics (traffic counters, stale) | relay process memory + optional PG persistence |

Key invariant: **a dispatcher needs zero rows in the console PG to
function**. A console can be unreachable indefinitely and a dispatcher
keeps running. The federation token is a single row on the dispatcher
side that names *who* it trusts; revocation is removing that row.

## 5. API surface

All admin APIs share path conventions: `/api/<resource>`, JSON, cookie
session, CSRF on writes. Schema is generated client-side from
hand-written TypeScript types in `console/src/types/` (no codegen
toolchain; the dispatcher is the contract, the console mirrors it).

### 5.1 Daemon localhost admin (v1.1 ships the endpoint, no UI)

| Method | Path | Purpose |
|---|---|---|
| GET | `/local/status` | current overlay state, peers, reflexive endpoint |
| PUT | `/local/alias` | rename self |
| POST | `/local/restart` | restart daemon (graceful) |
| POST | `/local/quit` | leave the network |
| POST | `/local/join` | join a network (token + dispatcher URL) |
| POST | `/local/upgrade` | trigger self-update |

Authenticated by a per-install token read from
`/var/db/gnet/admin_token` (Linux) or `/Library/Application Support/gnet/admin_token` (macOS),
mode 0400 owned by the daemon's user; the future native app reads it via
a Helper with privilege escalation. Bound to `127.0.0.1` only.

### 5.2 Dispatcher admin API

Auth and identity:

| GET | `/api/host-role` → `"dispatcher"` |
| POST | `/api/auth/login` (local username + password) |
| POST | `/api/auth/logout` |
| GET | `/api/auth/me` |

Network and devices:

| GET | `/api/network` → network meta |
| PUT | `/api/network` (settings) |
| GET | `/api/devices` → list with last snapshot |
| GET | `/api/devices/:pubkey` → device detail + recent admin snapshots |
| PUT | `/api/devices/:pubkey/alias` |
| POST | `/api/devices/:pubkey/kick` |
| POST | `/api/devices/:pubkey/restart` (forwarded to the daemon via the relay or via a future control channel) |
| POST | `/api/devices/:pubkey/rotate-key` |

Relays:

| GET | `/api/relays` → registered relay endpoints + health |
| POST | `/api/relays` (add) |
| DELETE | `/api/relays/:id` |

Audit and federation:

| GET | `/api/audit?from=…&limit=…` |
| POST | `/api/federation/handshake` (SaaS calls with a vending token) |
| POST | `/api/federation/operate` (SaaS-proxied admin op, federation-token authenticated) |
| GET | `/api/federation/status` |

### 5.3 Relay admin API (lite)

| GET | `/api/host-role` → `"relay"` |
| POST | `/api/auth/login` |
| GET | `/api/peers` → active forwarding entries |
| GET | `/api/traffic` → counters (pps, Bps, per-peer top-N) |
| GET | `/api/audit` |

### 5.4 Console federation API (gnet.golia.jp)

| GET | `/api/host-role` → `"console"` |
| GET | `/api/auth/oauth/{google,github,apple}/start` |
| GET | `/api/auth/oauth/{google,github,apple}/callback` |
| POST | `/api/auth/email/login` |
| POST | `/api/auth/email/register` |
| GET | `/api/auth/me` |
| GET | `/api/networks` → all networks visible to the user |
| POST | `/api/networks` (Mode A: provision a SaaS-hosted dispatcher) |
| POST | `/api/networks/register` (Mode C: register a self-host dispatcher by federation token) |
| GET | `/api/networks/:id` → metadata + dispatcher endpoint |
| `*` | `/api/networks/:id/proxy/*` → transparently proxies to the dispatcher's `/api/*` |
| GET | `/api/audit/aggregate` |

The proxy route is what makes the same SPA work in Mode A and C: the
browser hits `/api/networks/:id/proxy/devices`, console adds the
federation token, forwards to `<dispatcher-endpoint>/api/devices`,
streams the response back. No SPA-side switching needed beyond putting
the network id in the URL.

## 6. Auth + federation

### 6.1 Local accounts (dispatcher & relay)

- Username + password (argon2id, default `m=64 MiB`, `t=3`, `p=4`).
- First-boot admin bootstrap: dispatcher prints a one-time setup URL on
  stdout when no admin user exists. URL has a short-lived setup token;
  visiting it lets the operator set the first admin password.
- Sessions in the binary's own Valkey instance, cookie-based,
  HttpOnly+Secure+SameSite=Lax, CSRF token in a header for writes.

### 6.2 SaaS accounts (console)

- OAuth: Google + GitHub + Apple. Each provider's `sub` is the immutable
  key in `oauth_identities`. Email from the provider is a snapshot.
- Email + password also supported (same argon2id parameters).
- Multi-provider linking: one user can link multiple OAuth identities +
  one email/password. We never auto-merge by email — linking is an
  explicit user action.
- Sessions in console's Valkey, same cookie shape as dispatcher.

### 6.3 Federation handshake (Mode C)

1. User signs into `gnet.golia.jp`, opens "Register existing dispatcher".
2. Console mints a single-use registration token (Ed25519-signed),
   expires in 15 minutes.
3. User pastes token in the dispatcher's admin UI ("Register with SaaS").
4. Dispatcher fetches `gnet.golia.jp/api/federation/verify`, verifies
   the signature, stores `(token, console_pubkey, user_id, granted_at)`
   in the federation trust table.
5. Console issues a long-lived **federation token** to be used as the
   bearer on all `/api/networks/:id/proxy/*` calls.
6. Dispatcher accepts requests bearing the federation token as if they
   were from a `role=owner` local admin.

Revocation: user deletes the federation row in the dispatcher UI **or**
revokes from the console. Per §16.2 the propagation is pull-based with
a 30-second cache:

- Each federation request on the dispatcher runs through a helper that
  looks up `<console_origin>/api/federation/verify?token_hash=…`.
- A positive verdict caches for 30 s in dispatcher's Valkey under the
  key `fed:verify:<token_hash>`.
- Operations on a no-cache whitelist (`device.delete`,
  `device.rotate-key`, `network.delete`, `relay.delete`) bypass the
  cache and require a fresh verify.
- Console-side revoke flips `user_networks.federation_revoked_at`;
  `/api/federation/verify` returns 403 from that moment. Worst-case
  revocation latency = 30 s for non-sensitive ops, 0 s for sensitive
  ops, and unbounded only if the console is unreachable (in which case
  the dispatcher fails *closed* on a stale-cache lookup older than 5
  minutes, returning 503 to the federation request — pick safety over
  availability).

### 6.4 SaaS-hosted dispatcher (Mode A)

In Mode A, console provisions a dispatcher tenant. The same federation
mechanism applies — the user's federation row in the dispatcher just
gets created at network-creation time instead of by paste, and the
dispatcher endpoint URL is internal to our infra. From the SPA's
perspective, Mode A and Mode C are identical past sign-in.

### 6.5 Daemon admin token

`/local/*` endpoint authenticated by a token file written at install
time. The token is the one bearer; not OAuth, not user-scoped (the
endpoint *is* root-on-the-machine, so anyone who can read the file owns
the machine anyway). Future native app reads the file via a privileged
Helper.

### 6.6 Email transport (password reset, future verification mails)

Per §16.4, all transactional mail goes through **`mailrs`** — our
in-house mail server living at `services/mailrs` in the devops repo.
The console binary takes SMTP host / port / user / password from env
(`MAILRS_SMTP_HOST`, `MAILRS_SMTP_PORT`, `MAILRS_SMTP_USER`,
`MAILRS_SMTP_PASSWORD`) and submits via plain RFC 5321 SMTP — no
vendor SDK dependency. The MCP at devops platform deploy time fills
the env values; for local dev they sit in `.env.local`.

For self-host installs (Mode B) without a `mailrs` instance, the
operator points the same env at their own SMTP relay; the console
binary doesn't care which. If the env is unset the binary still boots
and serves the UI but disables password-reset / verification flows
with a clear "email transport not configured" message — self-host
without email is a valid, supported mode.

## 7. Multi-tenancy (Mode A only)

Mode A means we run dispatchers for many users. Two designs:

- **One dispatcher process, many networks** (`network_id` column on
  every dispatcher table). Simpler operationally; one binary, one PG,
  one Valkey. Logical isolation only.
- **One dispatcher process per user/network** (process-per-tenant).
  Stronger isolation; more moving parts; orchestration via systemd
  templates or k8s.

**Decision: one process, many networks.** Simpler, ships sooner, and
the same binary runs unchanged on a self-host user's machine (where
`network_id` is just always the single row). We pay for the upgrade
later if we hit a tenant we don't trust on a shared process — for v1.1's
audience (us + small open-source users + early SaaS users) the trade-off
is right.

Schema implication: every dispatcher-side table has `network_id UUID
NOT NULL`. The self-host case sets it to a fixed UUID generated at
first-boot.

## 8. Schema sketches

These are sketches, not the final migrations. The final migrations land
when each surface is concretely implemented.

### 8.1 Dispatcher schema (`gnet-discover-schema`)

```sql
CREATE TABLE networks (
    id              UUID PRIMARY KEY,
    name            TEXT NOT NULL,
    overlay_v4_prefix BYTEA NOT NULL,
    overlay_v6_prefix BYTEA NOT NULL,
    settings        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE admin_users (
    id              UUID PRIMARY KEY,
    network_id      UUID NOT NULL REFERENCES networks(id) ON DELETE CASCADE,
    username        TEXT NOT NULL,
    password_hash   TEXT NOT NULL,
    role            TEXT NOT NULL CHECK (role IN ('owner', 'admin')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (network_id, username)
);

CREATE TABLE devices (
    id              UUID PRIMARY KEY,
    network_id      UUID NOT NULL REFERENCES networks(id) ON DELETE CASCADE,
    x25519_pubkey   BYTEA NOT NULL,
    mlkem_ek        BYTEA NOT NULL,
    alias           TEXT NOT NULL,
    vip_v4          INET NOT NULL,
    vip_v6          INET NOT NULL,
    device_token_hash BYTEA NOT NULL,
    relay_eligible  BOOLEAN NOT NULL DEFAULT false,
    last_reflexive  TEXT,
    last_seen_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (network_id, x25519_pubkey),
    UNIQUE (network_id, alias)
);

CREATE TABLE device_snapshots (
    id              BIGSERIAL PRIMARY KEY,
    device_id       UUID NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
    taken_at        TIMESTAMPTZ NOT NULL,
    snapshot        JSONB NOT NULL          -- admin snapshot from the daemon push
);
CREATE INDEX device_snapshots_device_taken_idx
    ON device_snapshots (device_id, taken_at DESC);

CREATE TABLE relays (
    id              UUID PRIMARY KEY,
    network_id      UUID NOT NULL REFERENCES networks(id) ON DELETE CASCADE,
    endpoint        TEXT NOT NULL,             -- "host:port"
    health          TEXT NOT NULL DEFAULT 'unknown',
    last_check_at   TIMESTAMPTZ
);

CREATE TABLE federation_trust (
    id              UUID PRIMARY KEY,
    network_id      UUID NOT NULL REFERENCES networks(id) ON DELETE CASCADE,
    console_origin  TEXT NOT NULL,             -- e.g. https://gnet.golia.jp
    console_pubkey  BYTEA NOT NULL,            -- Ed25519, the SaaS verifying key
    granted_user_id UUID NOT NULL,             -- the console-side user id this trust represents
    token_hash      BYTEA NOT NULL,            -- hash of the long-lived federation token
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at      TIMESTAMPTZ
);

CREATE TABLE audit_log (
    id              BIGSERIAL PRIMARY KEY,
    network_id      UUID NOT NULL REFERENCES networks(id) ON DELETE CASCADE,
    occurred_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    actor_kind      TEXT NOT NULL,             -- 'local_admin', 'federation', 'system'
    actor_id        TEXT NOT NULL,             -- admin_users.id, federation_trust.id, or 'system'
    action          TEXT NOT NULL,
    target          TEXT,
    detail          JSONB NOT NULL DEFAULT '{}'
);
```

### 8.2 Console schema (`gnet-console-schema`)

The 0001 baseline (users + oauth_identities) survives. Additions:

```sql
CREATE TABLE email_credentials (
    user_id         UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    password_hash   TEXT NOT NULL,
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE user_networks (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    network_label   TEXT NOT NULL,             -- user-facing name
    mode            TEXT NOT NULL CHECK (mode IN ('saas', 'self_host')),
    dispatcher_endpoint TEXT NOT NULL,         -- https://dispatcher.example.com
    federation_token_hash BYTEA NOT NULL,      -- hash of the long-lived token
    role            TEXT NOT NULL DEFAULT 'owner',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, network_label)
);

CREATE TABLE audit_aggregate (
    id              BIGSERIAL PRIMARY KEY,
    user_id         UUID NOT NULL,
    network_label   TEXT NOT NULL,
    -- mirrored fields from dispatcher's audit_log; pulled by a periodic job
    occurred_at     TIMESTAMPTZ NOT NULL,
    actor_kind      TEXT NOT NULL,
    actor_id        TEXT NOT NULL,
    action          TEXT NOT NULL,
    target          TEXT,
    detail          JSONB NOT NULL DEFAULT '{}'
);
```

Email/password lives in `email_credentials` (separate table) so a
user's password row can be absent without making `users.password_hash`
nullable everywhere. (0001's `users.password_hash` column will be
dropped in the next migration; what's currently there is harmless dead
weight and can come out cleanly.)

## 9. Frontend layout

```
console/
  package.json           Vite 7 + React 19 + Tailwind 4
  index.html
  src/
    main.tsx
    App.tsx              top-level router; loads /api/host-role, mounts the right shell
    shells/
      DispatcherShell.tsx
      RelayShell.tsx
      ConsoleShell.tsx
    routes/
      dispatcher/        Devices.tsx, DeviceDetail.tsx, Network.tsx, Relays.tsx, Audit.tsx, Settings.tsx
      relay/             Peers.tsx, Traffic.tsx, Audit.tsx, Settings.tsx
      console/           Networks.tsx, NetworkProxy.tsx (wraps DispatcherShell over the federation proxy URL), Account.tsx, Audit.tsx
    types/               hand-written API types mirroring dispatcher / console / relay
    api/                 fetch wrappers, react-query hooks
    atoms/               Jotai atoms for session, current network, etc.
  dist/                  Vite output (gitignored), embedded into the three binaries
```

The federation proxy view (`routes/console/NetworkProxy.tsx`) literally
mounts the dispatcher shell with its base URL rewritten to
`/api/networks/:id/proxy/`. One UI, two locations.

Build: `bun run build` produces `console/dist/`. The three Rust binaries
each have a `build.rs` that ensures `console/dist/index.html` exists
(fails the build otherwise, with a clear "run `bun run build` first"
message). The Rust side uses `include_dir!("../../console/dist")`.

Version sync (per §16.6): `console/package.json` `version` must equal
the Rust workspace `version`. A small `scripts/check-versions.sh`
called from CI compares the two and exits non-zero on mismatch; the
release process bumps both fields in the same commit.

## 10. Deployment

### 10.1 Self-host (`docker-compose.yml`)

```
services:
  dispatcher:
    image: ghcr.io/goliajp/gnet-dispatcher:1.1.0
    ports:
      - "65432:65432"       # coord (UDP)
      - "8765:8765"         # admin web (TCP)
    env_file: .env
    depends_on: [db, kv]
  relay:
    image: ghcr.io/goliajp/gnet-relay:1.1.0
    ports:
      - "65433:65433/udp"
      - "8766:8766"         # admin web (TCP)
    env_file: .env
  db:
    image: postgres:18
    volumes: [pgdata:/var/lib/postgresql/data]
    env_file: .env
  kv:
    image: valkey/valkey:9
    volumes: [kvdata:/data]
volumes:
  pgdata:
  kvdata:
```

The `.env` template ships with the binaries; `make init` walks the
operator through admin password, overlay CIDR, advertised endpoint.

Per §16.1 the dispatcher admin port (`:8765` in the compose snippet
above) binds `0.0.0.0` by default — reachable from the LAN. The first
log line on dispatcher startup is the loud warning telling the
operator to firewall it if they did not intend LAN access. Localhost-
only is a one-line `.env` flip (`GNET_DISPATCHER_ADMIN_BIND=127.0.0.1:8765`),
not the default.

### 10.2 SaaS (`gnet.golia.jp` on t01)

- Per [[v1_1-deploy-target]], the SaaS console + its backing
  dispatcher(s) run **on t01 directly**, not via t01 → lx64 forwarding.
- Postgres 18 and Valkey 9 run on t01 — likely as systemd units rather
  than docker on the SaaS side, since t01 is sudoer Linux and the
  daemon's own systemd posture is already that style.
- Caddy on t01 terminates TLS for `gnet.golia.jp`, reverse-proxies to
  the console binary on a local port.
- Registration goes through the `devops.golia.jp` flow (project →
  service → caddy site → DNS A record → first deploy). Don't register
  the project until the console binary boots cleanly with `/health` and
  `/ready` green against the t01 PG.
- Per §16.8, the SaaS namespace is **`*.gnet.golia.jp`** — every user-
  visible network lives at `<network-slug>.gnet.golia.jp`. The Caddy
  site block uses a wildcard `tls` directive against the apex
  certificate, and the DNS record at `devops.golia.jp/api/dns/records`
  is a wildcard A record `*.gnet.golia.jp → 18.179.107.143`
  (`proxied: true`). The apex itself (`gnet.golia.jp`) serves the
  marketing landing + sign-in flow; the per-network host is only
  visible after sign-in.
- Per §16.5, OAuth provider credentials and any other ambient secrets
  the console binary needs at runtime live in `.env.local`, gitignored.
  A `.env.local.example` template lists the required keys
  (`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`,
  `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`,
  `APPLE_OAUTH_CLIENT_ID`, `APPLE_OAUTH_CLIENT_SECRET`,
  `MAILRS_SMTP_HOST`, …) with empty values; CI / devops platform
  populate real values at deploy time.

## 11. Security

- **TLS.** Public-facing surfaces (gnet.golia.jp) terminate TLS at Caddy.
  Self-host defaults to plain HTTP on a `0.0.0.0` bind (§16.1) —
  operators wanting TLS front it with their own reverse proxy + cert.
  We document this; we do not bundle Caddy in self-host (out of scope).
- **Admin bind default is LAN-reachable, not loopback** (§16.1). The
  dispatcher prints a loud warning on startup naming the LAN address
  the admin port is reachable on; operators who want loopback flip a
  single env var. This is a deliberate UX trade — a default that's
  invisible-but-secure forces every new self-host operator to
  reconfigure on day one, which is the worse default.
- **CSRF.** Cookie session + `X-Csrf-Token` header on writes. Token
  rotated on login.
- **Federation token storage.** Console stores a **hash** of the
  federation token, never the plaintext. Token plaintext is shown to the
  user once (and to the dispatcher during handshake) and never again.
- **Argon2id.** Same parameters across dispatcher local accounts and
  console email credentials. Parameters live in a single constant in a
  shared crate (or `gnet-adminapi`) so we can bump in one place.
- **Audit immutability.** `audit_log` is append-only at the SQL level
  (no UPDATE/DELETE grants for the application role; migrations use a
  separate role).
- **Daemon admin token.** File mode 0400; daemon refuses to start if
  the file is world-readable.
- **Rate limit auth endpoints.** Brute-force defense in front of every
  `/auth/login` and `/auth/oauth/callback`.

## 12. Migration from v1.0

A v1.0 deployment's coord stores `state.json`. The v1.1 dispatcher binary,
on first boot, looks for `GNET_DISCOVER_STATE_PATH` (existing env var); if
the file exists and the dispatcher PG is empty, it imports the JSON into
the new tables (`networks`, `devices`) under a single freshly-minted
`network_id`. The original JSON is renamed `.imported` so a second boot
doesn't double-import.

The internal fleet's switch-over goes:

1. Stand up the new dispatcher + PG + Valkey on a sibling host (not t01
   yet) and validate the import against a copy of t01's `state.json`.
2. Confirm the dispatcher serves the v1.0 coord wire protocol unchanged
   (no node-side breakage during cut-over).
3. On t01: stop `gnet-discover` service, copy `state.json` aside, start
   new dispatcher with PG pointing at the imported state, restart
   `gnet@main` on each node — they re-register, the snapshot table fills.
4. Hold for the v1.0 observation window plus a v1.1 observation window
   before exposing `gnet.golia.jp` to anyone external.

## 13. Testing strategy

- **Existing data-plane tests** (the entire `crates/gnet*` test corpus,
  KAT vectors, fuzz harnesses) keep running unchanged.
- **Dispatcher integration tests** — spin a real PG18 in `compose-dev`,
  run a small fleet of headless `gnet` daemons against it via
  `tokio::test`, assert admin API responses match dispatcher state.
- **Federation integration tests** — spin console + dispatcher
  together, perform handshake, perform a proxied operation, assert
  audit rows on both sides.
- **SPA tests** — Vitest for unit; Playwright for one end-to-end per
  shell (dispatcher / relay / console). The Playwright environment runs
  the real Rust binaries; no mocks of our own API.
- **Self-host smoke** — CI job: `docker-compose up`, wait for ready,
  hit a scripted "add a device" flow, assert green.
- **Upgrade smoke** — start a v1.0 coord with a populated `state.json`,
  shut down, start the v1.1 dispatcher pointed at the same file, assert
  the device count matches and a daemon can re-register.

CI keeps `warnings = deny` and `clippy::all = deny`. The new crates
inherit those lints. Frontend gets ESLint + TypeScript strict.

## 16. Decisions

The Open Questions from the rev1 draft were all answered on 2026-06-03.
Recorded here as the binding decisions for v1.1 code:

1. **Dispatcher admin bind default → `0.0.0.0`.** No `localhost-only`
   default. The binary prints a startup warning that the admin port is
   reachable from the LAN unless the operator firewalls it; the
   operator opts *out*, not in. Rationale: self-host installs land on a
   Linux box that's expected to be admin'd from another machine on the
   network — defaulting to loopback would force every operator to
   immediately reconfigure on day one, which is a worse default than
   "exposed but warned." See §11 for the security wording.
2. **Federation token revocation propagation → short-TTL pull, with a
   sensitive-op no-cache override.** Dispatcher validates the federation
   token against `<console-origin>/api/federation/verify` on each
   federation request, caches the verdict for **30 seconds**, and skips
   the cache for a small whitelist of high-blast-radius operations
   (`device.delete`, `device.rotate-key`, `network.delete`,
   `relay.delete`). Pull-based because a self-host dispatcher behind
   NAT can't reliably accept a push from the console; 30 s caps
   revocation latency at a level the user is told about up front. Cache
   key is the token hash; cache lives in dispatcher's Valkey.
3. **SaaS-provisioned dispatcher → same `gnet-discover` binary, multi-
   network via `network_id`.** Same code path the self-host runs. We
   accept logical isolation only and document it; if it ever proves
   inadequate we move dedicated tenants to a separate process without
   any code change (just a different config). The schema already
   carries `network_id` everywhere for this.
4. **Email transport → `mailrs`** (our in-house mail server at
   `services/mailrs` in the devops repo). Config goes in via the
   `mailrs` MCP at deploy time — the console binary takes SMTP host /
   port / user / password from env, no SDK dependency on a vendor mail
   service.
5. **OAuth provider client_id / client_secret → `.env.local` in the
   repo, gitignored.** Same pattern for any other ambient secret the
   console binary needs at runtime. CI loads them from devops platform
   secrets at deploy time; local dev populates `.env.local` from a
   `.env.local.example` template. Add `.env.local` to `.gitignore` as
   the first task in the console implementation.
6. **`console/` (TypeScript) version tracks the workspace version.**
   The SPA's `package.json` `version` field is bumped together with the
   Rust workspace `version` field. CI fails the build if they diverge
   (a small script in CI cross-checks the two values). Single source of
   truth: the Rust workspace version.
7. **Native node app → `mac/` subdirectory of this repo.** Not a
   sibling repo. Same versioning, same release tag covers daemon +
   console + native app. The daemon's localhost admin contract
   (§5.1) is therefore co-located with its only consumer.
8. **SaaS per-network domain → `<network>.gnet.golia.jp` subdomain.**
   Requires a wildcard `*.gnet.golia.jp` Caddy `tls` block + wildcard
   DNS A record (Cloudflare API supports this) + the console router
   resolving the leftmost label as the network slug. URL-path scoping
   (`gnet.golia.jp/networks/:id`) was rejected for worse UX and worse
   cookie isolation between networks.
9. **Telemetry → none from self-host, infrastructure-level only from
   SaaS.** Self-host binaries make zero outbound calls to anything we
   host (already a hard rule from §1). The SaaS console runs on our
   own infrastructure, so we collect at the *infrastructure layer*
   (Caddy access logs, systemd journals, Prometheus from the binary's
   `/metrics` endpoint exposed to localhost only) — no telemetry
   beacon in the binary itself, no `usage_events` table, no opt-in /
   opt-out toggle. A self-host install bit-for-bit equals the SaaS
   binary; only the deployment environment differs.

## 17. Phasing (engineering order, not ship order)

Even though we ship in one go, work has dependencies. Suggested order:

1. **Dispatcher PG schema + state importer.** Get state.json → PG
   round-tripping. No API surface yet.
2. **Dispatcher admin API skeleton + local auth.** Auth + read endpoints
   (devices, network). No write paths yet.
3. **SPA skeleton + dispatcher shell.** Read-only dispatcher UI working
   over the dispatcher's own dev server. Console shell stubbed.
4. **Node → dispatcher push channel.** Daemon POSTs admin snapshots;
   dispatcher stores in `device_snapshots`; UI shows them.
5. **Console scaffolding + OAuth + email auth.** Console binary serves
   its own SPA shell; can sign in; "no networks" empty state.
6. **Federation handshake + proxy route.** Console can register a
   self-host dispatcher and round-trip read requests.
7. **Dispatcher write paths.** Rename / kick / restart / audit.
8. **Relay admin (lite).** Smallest of the three, last.
9. **Daemon localhost admin endpoint** (no UI). Lands the v1.1 wire
   contract for the future native app.
10. **Self-host `docker-compose` packaging and first-boot UX.**
11. **`gnet.golia.jp` deploy via `devops.golia.jp`** (only after the
    internal fleet has dogfooded the federation path).
12. **Hardening sweep + ASVS audit + release.**

Each step is testable on its own; nothing in step N requires step N+1.
Steps 1–3 already started: phase B's `gnet-console` skeleton + the
console schema baseline live; steps 1–2 require the new
`gnet-discover-schema` crate to start.

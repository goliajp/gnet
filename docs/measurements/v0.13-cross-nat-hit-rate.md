# v0.13 — cross-NAT hit-rate measurement

Carve-out from v0.11 / v0.12: those shipped the symmetric-NAT port-prediction
sequential half (`gnet_punch::predict::CandidateSet` + the dial fan-out wiring)
under unit-test coverage. This is the in-vivo measurement of how often that
fan-out actually catches a peer's NAT mapping in practice, on Linux netns +
`iptables MASQUERADE`.

## Test topology

Five network namespaces glued by a host bridge:

```
                      ┌────────────┐
                      │   mock-c   │ rendezvous coord (gnet daemon, no NAT)
                      │ 10.99.0.30 │
                      └─────┬──────┘
                            │ veth-c
                  ┌─────────┴─────────┐
                  │  br-mocknat       │ host bridge — 10.99.0.1/24
                  └──┬───────────┬────┘
             veth-ao │           │ veth-bo
              ┌──────┴──────┐ ┌──┴───────────┐
              │ mock-a-nat  │ │ mock-b-nat   │ NAT routers
              │ 10.99.0.10  │ │ 10.99.0.20   │ ip_forward=1
              │ 192.168.10.1│ │ 192.168.20.1 │ iptables MASQUERADE
              └──────┬──────┘ └──────┬───────┘
               veth-ai│          veth-bi│
              ┌──────┴──────┐ ┌────────┴────┐
              │ mock-a-inner│ │ mock-b-inner│ peer daemons
              │ 192.168.10.2│ │ 192.168.20.2│
              └─────────────┘ └─────────────┘
```

`tc qdisc … netem delay 25ms` is added on each NAT-outer veth so the
round-trip between any two NAT'd peers is ~100ms. In raw netns the RTT is
sub-millisecond — too tight for DCUtR's simultaneous-open timing
(`dial_at = sync_send + RTT/2`), where the origin's fan-out arrives at the
target's NAT before the target's fan-out has populated its conntrack table.

## NAT modes

| Mode | iptables flag | Behaviour |
|---|---|---|
| Mode 1 | (default) | port-preserving: same external port as inner source port when free, reused across destinations |
| Mode 2 | `--random-fully` | per-flow randomised external port across the Linux ephemeral range `32768..=60999` |

Mode 1 is the most common consumer/SOHO NAT behaviour
(default Linux MASQUERADE on OpenWrt, iptables on Ubuntu servers, vendor
router stacks that match endpoint-independent mapping semantics). Mode 2 is
the worst case (true symmetric NAT under fully randomised port allocation).

## Trial mechanics

Per trial:

1. Tear down topology (drops all netns / conntrack).
2. Bring up topology with the current NAT mode.
3. Start three fresh `gnet up` daemons in mock-c / mock-a-inner / mock-b-inner.
4. Pre-warm: mock-a and mock-b both ping mock-c's overlay address. This
   establishes direct sessions and lets mock-c learn both peers' endpoints
   (it has to relay the punch coordination traffic afterwards).
5. TUN-side trigger: ping mock-a → mock-b. mock-a falls back to relay path
   via mock-c (no static endpoint for mock-b, no `relay_eligible` peer in
   static config). After session is up, the 30s direct-upgrade timer fires
   `start_punch`, which runs the full DCUtR rendezvous + 65-candidate fan-out.
6. Poll `mock-a.log` for the `PUNCH-SUCCESS` marker. Outcome:
   - `HIT_SLOT0` — `endpoint == observed`, the slot-0 hit-detection branch
   - `HIT_CORRECTED` — `endpoint` was corrected to a non-slot-0 candidate
   - `MISS` — no marker after 15s
7. Stop daemons.

`DIRECT_UPGRADE_BASE` was tightened from 30 s to 3 s and three `eprintln!`
markers (`start_punch`, `dial_fanout`, `complete_initiation` outcome) were
added — both as a **test-only** patch on the lx64 build, NOT shipped.

## Reproducing

```bash
# On lx64 (Debian 13, kernel 6.12, iptables-nft):
git clone https://github.com/goliajp/gnet ~/workspace/goliajp/gnet
cd ~/workspace/goliajp/gnet
cargo build --release -p gnet

# scripts (in this repo)
docs/measurements/v0.13/setup-topology.sh    # topology setup/teardown
docs/measurements/v0.13/start-daemons.sh     # daemon lifecycle
docs/measurements/v0.13/run-trials.sh        # one-mode N-trial harness

NAT_MODE=default      bash docs/measurements/v0.13/run-trials.sh 30
NAT_MODE=random-fully bash docs/measurements/v0.13/run-trials.sh 30
```

Raw per-trial outcomes land in `results-<MODE>.tsv` (one row per trial:
`trial`, `outcome`, `detail`).

## Measured results

Ran on lx64 (Debian 13, kernel 6.12.74, x86_64 i7-10700K, iptables-nft).
Raw per-trial outcomes in `v0.13/results-default.tsv` and
`v0.13/results-random-fully.tsv`.

### Mode 1 — default MASQUERADE

|     | slot-0 | corrected | miss | total | hit-rate |
|-----|------:|---------:|----:|-----:|--------:|
| N = 30 | 30 | 0 | 0 | 30 | **100.0 %** |

Default Linux MASQUERADE is port-preserving: the same internal
`(src_ip, src_port)` maps to the same external port regardless of
destination, so `P_AC == P_AB` and the observed-endpoint slot-0 of the
fan-out hits trivially. Predicted 100 %, measured 100 %.

### Mode 2 — MASQUERADE `--random-fully`

|     | slot-0 | corrected | miss | total | hit-rate |
|-----|------:|---------:|----:|-----:|--------:|
| N = 30 | 0 | 0 | 30 | 30 | **0.0 %** |

`--random-fully` randomises the NAT-allocated external port per flow
across the Linux ephemeral range `32768..=60999` (28 232 ports).
Sequential ±32 covers 65 / 28 232 ≈ 0.23 % of that range, so neither
slot-0 nor any non-zero offset hits within the candidate window.
Predicted ≈ 0 %, measured 0 %.

## Interpretation

Mode 1 covers the most common consumer / SOHO NAT deployments (default
Linux MASQUERADE on OpenWrt, iptables on Ubuntu hosts, vendor stacks
that match endpoint-independent-mapping semantics). v0.12's fan-out
wire adds no measurable overhead and works on the fast path.

Mode 2 is the worst case under fully-randomised port allocation. The
sequential half is the wrong tool for this distribution; the random
half (`gnet_punch::predict::birthday_hit_probability`, already shipped
in the predict crate's API) is what covers it. Wiring the random half
into `dial_fanout` — with the deeper retry semantics needed to keep
both ends' fan-outs aligned across multiple rounds — is the v0.14+ work
item.

Real symmetric NATs in the field (consumer routers with incremental
walk on collision, CGNAT with deterministic next-port allocation) land
much closer to Mode 1 than Mode 2, so v0.12's sequential half fires on
a meaningful slice of real-world traffic.
